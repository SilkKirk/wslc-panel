## 1. P0：正确性 / 隐患

### 1.1 `AppState::new` 把凭据档**读了两遍**，而注释说只读一遍 —— 确认

`crates/wslc-panel-core/src/state/app.rs:310-313` 的注释：

```rust
// 只读一次盘，然后把两半分别放进结构体 —— 对比上面 `db_credentials`
// 那两行（各调一次 `db_credentials_at_startup()`，白读一遍）。
let (deploy_store, deploy_store_error) = deploy_store_at_startup();
```

但同一个 `Self { … }` 里（`app.rs:350-351`）：

```rust
db_credentials: db_credentials_at_startup().0,
db_credentials_error: db_credentials_at_startup().1,
```

`db_credentials_at_startup()`（`state/db_state.rs:10`）内部是
`DbCredentialStore::load(store_path(app_dir()))` —— **一次文件读 + JSON 解析**。
于是：启动时读两遍；两次读之间文件若被改（另一个面板实例刚写过），
`store` 和 `error` 会来自**不同次读取**，出现"存档读成功、错误却非空"这种自相矛盾的状态。

**修法**（1 行 + 1 个绑定）：

```rust
let (db_credentials, db_credentials_error) = db_credentials_at_startup();
// … Self { db_credentials, db_credentials_error, … }
```

**风险**：零。`core` job 直接编译覆盖；`state/tests/app.rs` 里已有相关断言。

### 1.2 「添加部署」弹窗**画了两排底部按钮**，两处 id 完全相同 —— 确认

`app/shell/dialogs.rs:1162-1202` 给 `DeployForm` 挂了 `.footer(modal_footer([cancel, submit]))`
（id：`deploy-cancel` / `deploy-submit`）；而 `views/deploy.rs:921-941` 在**内容区**里又画了一份
一模一样的 `modal_footer`，**同两个 id**。

后果：弹窗底部一排「取消 / 部署」，内容最下面又一排；两处**同 id 的元素在同一帧同时存在**
（GPUI 的 hover / active 状态按元素 id 记，重复 id 是已知会互相干扰的）。
而且内容区那一排在 `#deploy-dialog-scroll`（`views/deploy.rs:678`，`.overflow_y_scroll`）里，
窗口矮时会随内容滚走 —— 表现为"有时一排、有时两排"。

**修法**：删掉 `views/deploy.rs:921-941` 整段 `.child(modal_footer([...]))`，并删掉该文件第 7 行的
`modal_footer` 导入（`views` 下只有这一处用它；`modal_footer` 的其他调用全在 `app/shell/`）。

**风险**：纯删除。少删导入会被 `lint`（阻塞）抓成 `unused import`，不会静默进 main。
**需本机实测**：打开「添加部署」与「重新部署」各一次，确认只剩底部一排、两个按钮都能点。

### 1.3 `Page::needs_window_to_enter()` 与 `Shell::set_page` 是**两处同一份知识** —— 待定

`state/nav.rs:153-159` 列出 4 个"要 window 才能进"的页面；
`app/shell/core.rs:811-874` 又把这 4 个页面各写了一个 `if page == Page::X`。

现在两边一致，但**没有任何东西保证它们以后一致**：往 `needs_window_to_enter` 里加第 5 页、
忘了加 `set_page` 的分支，表现是"页面进得去，但输入框没建"——
再由 `views/mod.rs:117-123` 的防御分支显示一句"请重新进入"。不崩，但很难查。

**修法**：`set_page` 改成对 `page` 的 `match`（穷举），并在 `_ => {}` 那一臂写一句
"不需要 window 的页面"；`needs_window_to_enter` 保留给 `nav` 的测试与 `Page` 的文档，
两者都由编译器盯着（`match` 漏了新变体是编译错误，这正是要的）。

**风险**：低（纯控制流重排）。**判据**：`core` 绿 + `set_page` 里不再出现 `==` 比较。

## 2. P1：重复实现（同一件事写了多遍）

### 2.1 `app/shell/dialogs.rs`：17 个分支 × ~40 行外壳 —— **本轮最大一块**

`dialogs.rs` 一共 1206 行，其中 `open_dialog_for`（226-1204）占 **约 980 行**，17 个臂。
逐臂比对后，**结构完全同构**：

| 每个臂都做 | 出现次数 |
|---|---|
| `let entity = cx.entity();` | 17 |
| `cx.new(move |cx| ShellView::new(...))` | 17（**所有**臂的 content 都是 `Entity<ShellView>`） |
| `let on_cancel = { … }`（Esc / 点遮罩 → 清状态 → `true`） | 15 |
| `window.open_dialog(cx, move |dialog, …| dialog.title(..).w(px(..)).overlay(true)…)` | 17 |

差异只有五样：**标题**、**宽度**、**`overlay_closable`**、**`keyboard`**、**footer 里那几颗按钮**。

**修法**：在 `dialogs.rs` 顶部加三个私有助手，臂里只留差异：

```rust
/// 把「读 Shell 状态画一块」包成会随 Shell 重画的子实体（17 个臂原本各写一遍）。
fn shell_view(
    entity: &Entity<Shell>,
    body: impl Fn(&Shell, &App) -> AnyElement + 'static,
    cx: &mut Context<Shell>,
) -> Entity<ShellView>;

/// 三条退出路径共用的「关掉并清状态」。
/// ⚠️ 返回 `true` 表示"允许关"；清状态必须在里面做完，否则下一帧会重开（AGENTS.md §7.5）。
fn close_handler(
    entity: &Entity<Shell>,
    close: impl Fn(&mut Shell, &mut Context<Shell>) + 'static,
) -> impl Fn(&ClickEvent, &mut Window, &mut App) -> bool + 'static;

/// 统一 open_dialog 的骨架：只收"差异那五样"。
struct DialogSpec {
    title: SharedString,
    width: f32,
    overlay_closable: bool,
    keyboard: bool,
    content: Entity<ShellView>,
    footer: Vec<AnyElement>,
}
fn open_shell_dialog(window: &mut Window, cx: &mut Context<Shell>, spec: DialogSpec);
```

**收益**：15 份 `on_cancel` 收敛成 1 份；每臂从 ~40 行降到 ~10 行，预计 **-400 ~ -500 行**。
更重要的是：以后加浮层只需要写"标题 + 内容 + 按钮"，**层序 / 遮罩 / Esc 语义不可能漏**
（v0.20.0 的出问题方式正是"某个臂忘了 `on_cancel`"）。

**风险**：中。
- `self` 的借用不能逃进 `'static` 闭包（`dialogs.rs:1031-1032` 已经踩过 `E0521`），
  所以标题 / 宽度 / `pulling` 这类值必须在**闭包外**算好再传进 `DialogSpec`；
- `on_cancel` 的返回类型必须是具体的 `impl Fn`，不能装箱（`Box<dyn Fn>` 会和 GPUI 的
  `Fn` 约束打架）—— 本仓库没有 `dyn` 先例，按 `impl` 写；
- 一次改 17 个臂编译面很大，但**没有行为变化**。`ui` job 是唯一判据。

### 2.2 `DialogKey` 的知识散在**四个地方**

同一个浮层的"开 / 关 / 标题 / 能不能关"分别写在：

| 知识 | 在哪 |
|---|---|
| 什么时候该开 | `dialogs.rs:94-188`（`sync_dialog_stack` 里 17 个 `if`） |
| 标题 / 宽度 / 可关性 | `dialogs.rs:234-1204`（`open_dialog_for` 的臂） |
| 关掉时清哪个状态 | 各域的 `close_*` 方法（`close_logs` / `close_pull_dialog` / …） |

**修法**（与 2.1 同批做，改的是同一个文件）：把"该不该开"收成 `DialogKey` 的方法：

```rust
impl DialogKey {
    /// 这一帧这个浮层该开着吗（**唯一**判据）。
    fn is_open(self, shell: &Shell) -> bool { … }
}
```

`sync_dialog_stack` 于是变成：

```rust
let desired: Vec<DialogKey> = DialogKey::ALL
    .iter()
    .copied()
    .filter(|key| key.is_open(self))
    .collect();
```

`DialogKey::ALL` 的顺序就是层序（现在由 17 个 `if` 的书写顺序隐式决定 ——
这正是"层序靠人工排序"那类风险的残余）。

**收益**：`sync_dialog_stack` 从 ~95 行降到 ~15 行；加浮层只改 `is_open` 一个臂。
**风险**：低-中。17 个 `is_open` 是纯读，`&Shell` 借用很容易写；但要逐条核
`db_form.is_some()` 这类"页面进得来"的门槛，一条都不能漏（漏了就是浮层自己弹出来）。

**顺带修一个"今天不可达"的层序坑**：现在 `Confirm` 在 `desired` 里排在 `DeployForm` / `WslConf` /
`PullImage` / `CreateContainer` / `DbAction` **之前**（`dialogs.rs:162` vs `:167/171/175/179/184`）。
一旦哪个表单弹窗内部再弹二次确认，确认框就会被压在表单**下面** —— 正是 v0.9.14 那类
"压缩磁盘的确认框在详情之下"的同型 bug；而 `AGENTS.md` 把 `Confirm` 描述成
"可以从**任何**浮层里弹出来"。今天全仓没有从表单 body 里调 `request()` 的地方，所以**不可达**；
但把 `Confirm` 挪到表的最后一行是一行改动、零行为变化 —— 顺手做掉。

### 2.3 `confirm_pending` 按**具体变体**分支 —— 动作的事后效应应该由动作自己说

`app/shell/core.rs:697-741` 在通用执行流程之前，对三种情况做了特判：

```rust
if let ConfirmAction::Container(PendingAction::DeleteDatabaseBackup { … }) = &action { … return; }
let dropped_database = match &action { … DropDatabase { .. } => Some((container, database)), _ => None };
let reload_db = matches!(action, … DropDatabase { .. } | DropUser { .. });
let close_detail = match &action { … Unregister { name, .. } => …, _ => false };
```

后果：**每加一个"删完要顺手做点什么"的动作，都要回到 `core.rs` 改这段**，
而 `wslc-panel-core` 里的 `ConfirmAction` 完全不知道有这回事 —— 知识放在了错误的一层。

**修法**：在 `wslc-panel-core/src/state/actions.rs` 增加一个**纯数据**的事后效应枚举：

```rust
/// 动作执行完之后界面要跟着做的事。**故意只描述、不执行** ——
/// 执行需要 `&mut Shell`，那是 UI 层的事。
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum Aftermath {
    None,
    /// 删库成功：把本地存档里的账号一起清掉。
    ForgetDbCredentials { container: String, database: String },
    /// 删库 / 删用户：重读数据库页那两张表。
    ReloadDbLists,
    /// 注销发行版：关掉它的详情（对象没了）。
    CloseDistroDetail,
    /// 「删除备份」不是一条命令：走它自己的三步执行路径。
    DeleteDbBackup { container: String, database: String, windows_path: String, container_path: String },
}

impl ConfirmAction {
    pub fn aftermath(&self, open_distro_detail: Option<&str>) -> Aftermath { … }
}
```

`confirm_pending` 只留：

```rust
match action.aftermath(self.distro_detail.as_deref()) {
    Aftermath::DeleteDbBackup { .. } => { …; return; }   // 分流
    other => aftermath = other,
}
```

**收益**：`core.rs` 里 4 段特判 + 一个 `#[allow(clippy::redundant_pattern_matching)]` 全删；
"这个动作做完还要干什么"和动作定义在**同一个文件**里；可以在 `core` job 里断言
（`state/tests/actions.rs` 已有 `every_distro_action_has_copy_too` 这种"遍历所有变体"的测试范式，
照着写一条"每个变体都有 aftermath"）。

**风险**：中（动了确认执行主路径）。**必须实测**：删库、删用户、注销发行版、删除备份各点一次。

### 2.5 `truncate` 在两个 crate 里各有一份

2. **全部叫 `*_page`**：`dashboard_page` / `instances_page` / `add_instance_page` /

   `deploy_page`（已有）/ `sql_console_page`（已有）/ `settings_page`（原 `app_settings`）。

代价：9 个函数名 + `views/mod.rs` 的 `use` 列表 + 分发处。收益：`views/mod.rs` 的
`use` 一眼就是"11 个页面"，且**不会**再出现"这个页面的入口叫 `config` 还是 `wsl_config`"。

### 3.2 `views/*` 里的 `pub fn` 应统一成 `pub(crate)`

但全模块 40 多个助手都是 `pub(crate)`，只有页面入口写成 `pub`

**风险**：零（`ui` job 会抓出任何可见性不足）。

## 5. 官方组件：本轮核实与结论

> 以下 API 结论来自 docs.rs 上 `gpui-component 0.8.0` 的公开页面（本机无 cargo、无源码）。
> 凡标"待 spike"的，**不要**按"看起来可以"直接改。

### 5.1 `tooltip`：**可以换** —— 官方 `.tooltip()` 就挂在普通 `div` 上

我上一版写的是"公开了但挂不到任意元素上"，**这条是错的**，本轮查官方文档时被推翻：

- gpui-base 在 `TooltipOverlay` 的文档里明写 **"This does not control GPUI's native `.tooltip()` API."**
  —— 也就是说 `.tooltip()` 是 **gpui 原生**提供的，根本不在 gpui-component 里（我上一版只查了 component）；
- gpui-kit 官方文档（`/zh-CN/component/tooltip`）给的**基础示例**就是普通 `div`：

```rust
div()
    .child("Hover me")
    .id("basic-tooltip")
    .tooltip(|window, cx| Tooltip::new("This is a helpful tooltip").build(window, cx))
```

- `Button::tooltip("…")` / `.tooltip_with_action(..)` 是组件自带的便捷写法；我们已有 6 处 `.tooltip(`
  在用（`common.rs:732/765`、`config.rs:290`、`db_dialogs.rs:123`、`details.rs:370`、`images.rs:144`），**都不动**。

**结论**：`common::cell_full` / `cell_link` 里拿 `Button::text()` 当"tooltip 壳"的写法可以去掉，
退回"`div` + `.id()` + `.tooltip(..)`"。收益不只是少一层：现在每一格都是一个 `Button`，
带按钮的焦点 / 键盘语义（虽然已经 `tab_stop(false)`），而 hover 状态按元素 id 记 —— 两个同 id 的
`Button` 会互相干扰（`cell_full` 的注释里就记着这条）。

**替换点只有两处**：`common.rs:716`（`cell_full`）与 `common.rs:752`（`cell_link`）。
**风险**：低 —— `.tooltip` 要求元素有 `.id()`，这两处本来就用 key 拼了唯一 id。
**必须实机确认**：悬停 5 个表格单元格，看 tooltip 出得来、长文本仍然 truncate。
**顺带必须改文档**：`AGENTS.md` §7.5 与 `common.rs:702` 那条"tooltip 是 `pub(crate)`、
只能借 `Button`"整段要换成本节的结论 —— **它现在会误导下一个人**（我就是照着它判错的）。

### 5.2 `notification`：**应该换** —— 官方就是应用内 toast，还比自绘的多一半能力

上一版我写"窗口级通知会盖住底部按钮"，**这也不成立**：官方 `NotificationDelivery` 默认是
`InApp`（**应用内 toast**），窗口右上角、可配 8 个 `Anchor`、最多堆 10 条、悬停暂停倒计时、
支持操作按钮与自定义内容。官方文档第一句就是"在窗口右上角显示支持自动消失的 toast 通知"。

现状（全部自绘）：`AppState::toast: Option<Toast>` 单槽 + `ToastKind` 3 档 +
`Toast::lifetime()`（4 / 8 秒）+ **500ms 轮询的 `start_toast_reaper`** + `render.rs:210-264` 的 55 行内联 UI，
调用点 **201 处**。

**迁移设计（关键是让这 201 处一行不改）**：

1. `Toast` 变成**一次性槽**：`notify()` 照旧 `self.toast = Some(t)`，但 `render` 里直接 `take()` 走，
   不再等它过期 —— 于是 `shown_at` / `lifetime()` / `clear_expired_toast` / `start_toast_reaper`
   整条时间线全删（含 `core.rs:201` 的启动调用）；
2. `Shell::render` 开头（`sync_dialog_stack` 旁边）加 ~10 行：
   ```rust
   if let Some(t) = self.state.toast.take() {
       // 先删同 id 的：保住"后弹的盖掉先弹的"这条现有语义
       window.remove_notification::<ToastNote>(cx);
       window.push_notification(
           Notification::new().message(strip_md(&t.text)).with_type(t.kind.into()),
           cx,
       );
   }
   ```
   `remove_notification::<T>` / `push_notification` 都是 `WindowExt` 的公开方法（已核）。
   单槽语义是**必须保住**的：`deploy/submit.rs:141` 有注释写着"这条更重要，后弹的会盖掉先弹的"；
3. `dismiss_toast` → `window.remove_notification::<ToastNote>(cx)`（`.on_click` 回调本来就能拿到 window）；
4. 删掉 `render.rs` 那 55 行提示条 UI，以及内容列最后那条 `.child(toast)`。

**收益**：少一个 500ms 常驻循环、少 55 行渲染、少一套 4/8 秒时长逻辑；多出悬停暂停、关闭按钮、
`id` 去重、以及将来"投到系统通知中心"（`NotificationDelivery::System`；Windows 要启动早期
`App::set_app_identity`）。

**必须先定的两件事（都只能实机定）**：
- **位置**：默认 `Anchor::TopRight`，而应用页头右上角正是「刷新」按钮（`render.rs:88-100`）。
  可全局改（`Theme::update(cx, |t| t.notification.placement = …)`）或单条覆盖。
  建议实机比较 `TopRight` / `TopLeft` / `BottomRight` 三个再定；
- **时长**：官方只给了 `autohide(bool)`，没给"每条多少秒"；而我们现在是"错误 8 秒、其余 4 秒"。
  迁移后按官方默认走；若错误嫌短，只能 `.autohide(false)`（那就得手动关，属产品决定）。
  ⚠️ 这条要在实机上掐一次表，**不要猜**。

**风险**：中 —— 动的是全局反馈通道，且 `render` 里 push 通知要确认不会自激重绘
（`sync_dialog_stack` 已经证明"在 render 里改窗口状态"是这套代码的既有做法，但通知是新的一类）。
**判据**：`ui` 绿 + 实机走一遍"成功 / 失败 / 长任务开始→结束"三类提示。

### 5.3 `progress`（线性条）：存在，但**没有已知总量**，不铺

`progress::Progress` 是线性进度条。本项目所有长任务的进度都是**增量**而非**比例**：

- 拉取镜像 / 导出 / 安装：只有"已写入多少字节"+"已用时"，总量在流式输出里拿不到
  （`cmd/install.rs` 的模块注释专门解释了为什么看产物大小而不是解析 `curl` 进度）；
- 备份 / 导入：同样只有"已处理"；
- 唯一有比例的是 Dashboard 四只环 —— 已经在用 `ProgressCircle`。

**结论：不换**。若哪天真拿到总量（比如 `install` 的 rootfs 有 `Content-Length`），
再给那一处加条 `Progress` —— 入口只有 `views/install.rs` 一个。

### 5.4 `resizable`：**可选的新增**（SQL 页左树可拖宽）

`resizable` 模块存在，且 crate 根就 re-export 了 `h_resizable` / `v_resizable` /
`resize_handle` / `resize_handle_appearance`。

现状：SQL 页左侧树是**固定 260px**，收起时 32px（`views/sql.rs:128-140` 的注释解释了为什么收起要留窄条）。
用户能看到的代价：表名很长时无法拖宽，只能靠 tooltip 看全名。

**建议**：作为**独立可选批次**先 spike（一个临时页签里放左右两块 + 一条拖拽条），
确认三件事再铺：① `ResizableState` 存哪（`Shell` 加实体字段）；② 收起/展开的 32px 窄条怎么与它共存；
③ 拖拽会不会和 `DataTable` 的虚拟滚动抢鼠标。
**不要**和 §8 的其它批次混在一起。

### 5.5 `clipboard`：存在 —— 记为**功能建议**，不是规范问题

命令预览（`views/create.rs:221` 的 `command_preview`）和日志目前只能手选复制。
官方 `clipboard` 模块可以做"一键复制"，但这是**产品新增**，不属于"统一/对齐"，
本文不把它列进批次；要做时单独开一条。

## 7. 测试：946 条很厚，缺口在哪

### 每批的固定收尾（本机没有 rustfmt，绕不过去）

1. 改完 → `git -c http.version=HTTP/1.1 push origin main`；
2. 轮询 `GET /commits/<sha>/check-runs`（要 `Count -gt 0` 且全部 `completed`，看 `conclusion`）；
3. `lint` 若红在 **rustfmt**：`workflow_dispatch` 跑 `fmt.yml`（`commit=true`）→ 拉回 `style: cargo fmt`；
4. **补一个空提交**（机器人推送不触发 job，否则 fmt 后的代码从未被编译验证）；
5. 再轮询一轮，确认三个 job 全绿。

> 实测：这一轮 10 个批次里，**有 5 次栽在 rustfmt、2 次栽在 clippy**
> （`redundant_closure` ×2、`unused` 0 次）。都不是逻辑错误，但都让 CI 红一轮。
